# Подбор внутреннего батча BGE-M3

`batch_capacity.py` загружает модель проекта **один раз** и напрямую вызывает
`model.encode` с разными `batch_size`. API и межпроцессные очереди не участвуют.
`INFERENCE_BATCH_SIZE` из `.env` не ограничивает перебор: размер передаётся явно.
Типы эмбеддингов одинаковы для всей серии и задаются через `--types`.

## Команды Just

Из папки `puper_test`:

```powershell
just                         # список команд
just options                 # справка без загрузки модели
just stop-worker             # освободить GPU от штатного воркера
just quick                   # короткий замер
just run                     # полная серия с настройками по умолчанию
just run --tokens 128 512 --batch-sizes 1 2 4 8 --types dense sparse --repeats 10
just start-worker            # вернуть штатный воркер после замеров
```

Выберите нужный запуск (`quick` или `run`); после завершения, ошибки или
прерывания запустите `just start-worker`. Команды замера сами не останавливают
и не запускают штатный воркер. Перед остановкой дождитесь завершения текущих
запросов. Результаты сохраняются в `puper_test/results/`.

Из корня проекта: `just --justfile puper_test/justfile quick`.
По умолчанию используется сервис `api`; другой можно задать через
`PUPER_TEST_SERVICE`. Для локальной справки Python можно переопределить
через `PUPER_TEST_PYTHON`. Docker-образ должен быть уже собран.

## Запуск на Radeon 880M / amd-wsl

Запускать из корня проекта. Остановите основной воркер на время замера, чтобы
его модель не занимала память GPU и не конкурировала за вычисления. Входящие
API во время замера будет недоступен; его очередь и результаты теряются при остановке.
Дождитесь завершения текущих
запросов перед остановкой. Сам скрипт не останавливает сервисы и не меняет `.env`.

PowerShell, короткая серия:

```powershell
docker compose stop api
try {
    docker compose run --rm --no-deps -v "${PWD}/puper_test:/app/puper_test" --entrypoint python api /app/puper_test/batch_capacity.py --tokens 128 --batch-sizes 1 2 4 8 --warmups 1 --repeats 3
} finally {
    docker compose start api
}
```

Вместо короткой команды внутри `try` для полной серии:

```powershell
docker compose run --rm --no-deps -v "${PWD}/puper_test:/app/puper_test" --entrypoint python api /app/puper_test/batch_capacity.py --tokens 32 128 512 2048 8192 --batch-sizes 1 2 4 8 16 32 --types dense --warmups 2 --repeats 5
```

Для dense + sparse замените `--types dense` на `--types dense sparse`.
Для отдельного ColBERT: `--types colbert`. Семь сочетаний можно проверить
отдельными запусками. Увеличивайте диапазон через `--batch-sizes`, если его
верхняя граница успешно пройдена и скорость продолжает расти.

Контейнер использует ту же модель, ревизию и FP16, что и штатный воркер.
Образ должен быть уже собран. Пересборка ради теста не нужна: папка монтируется.
Запускается отдельный процесс модели, а не второй GPU process-воркер.
Для CPU / native AMD замените имя сервиса на `api` / `api` при
соответствующем окружении. Справка без загрузки модели:

```powershell
.venv/Scripts/python.exe puper_test/batch_capacity.py --help
```

## Что измеряется

- По умолчанию: длины до 32, 128, 512, 2048, 8192 токенов; батчи 1–32;
  два прогрева и пять измерений на каждую пару. Прогревы не входят во время.
- Тексты синтетические, одинаковые внутри батча. Длина включает специальные
  токены; фактическое число, бюджет и SHA-256 текста записываются в отчёт.
  Фактическая длина может быть немного меньше бюджета.
- Измеряется весь `model.encode`: токенизация, вычисления и перенос результатов
  на CPU, включая обработку sparse / ColBERT библиотекой. Запись JSON и проверка
  результата не входят в таймер. GPU синхронизируется на границах замера.
- Записываются все времена, медиана, минимум / максимум, тексты/с и входные
  токены/с. Скорость = все обработанные тексты / суммарное измеренное время.
- Память: `peak_allocated_bytes` и `peak_reserved_bytes` аллокатора PyTorch,
  включая модель. Это не вся занятая память GPU и не пик RAM процесса.
  При OOM во время прогрева сохраняется пик этого прогрева.
- Установленная FlagEmbedding делает дополнительный пробный forward внутри
  `encode`; он входит во время. Размеры реальных forward записываются в
  `forward_shapes` для каждого измерения.

## Защита от скрытого уменьшения батча

FlagEmbedding может перехватывать ошибки `RuntimeError` / OOM и автоматически
уменьшать батч. Для этого теста forward обёрнут так, чтобы ошибка вышла наружу
без повторной попытки с меньшим размером. Проверяется, что каждый реальный
forward получил запрошенное число текстов. Штатный код проекта не изменяется.

При OOM сохраняется строка `oom`; большие размеры **для той же длины**
пропускаются. Следующая длина проверяется заново. Прочие ошибки останавливают
серию с кодом 1, Ctrl+C — с кодом 130. Обработанный OOM — результат измерения,
а не ошибка скрипта. После серьёзной ошибки GPU контекст может потребовать
нового процесса; последующая ошибка будет сохранена и остановит серию.

## Как читать результат

JSON появляется в `puper_test/results/` и обновляется после каждого сценария;
при обработанной ошибке и Ctrl+C сохраняются уже законченные сценарии.
При принудительном завершении текущий замер может потеряться.

В `summary` для каждой длины:

- `fastest_tested_batch` — лучший из проверенных по текстам/с;
- `smallest_batch_within_5_percent_of_peak` — меньший батч со скоростью не ниже
  95% лучшей, кандидат для меньшей задержки;
- `largest_successful_tested_batch` — самый большой успешный из проверенных;
- `first_failed_batch` — первый OOM в проверенном диапазоне, если был.

Это не доказательство абсолютного максимума. Для рабочего значения оставьте
запас памяти и перепроверьте реальные тексты, смешанные длины и длительную
нагрузку. Однородные синтетические тексты не отражают потери на padding при
разной длине. Тест не включает ожидание наполнения динамического батча и
не меняет рабочую настройку автоматически.
