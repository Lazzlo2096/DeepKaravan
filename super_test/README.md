# Нагрузочная проверка celery-amd

`celery_amd_capacity.py` проверяет настоящий тракт **публикация Celery → Redis →
AMD-воркер → сохранённый результат**. Это отдельный запуск по явной команде:
обычный `pytest` его не собирает. Тест не запускался при создании.

Один Celery message — одна задача `deepkaravan.embed` с JSON-объектом:
обязательные `model: "baai/bge-m3"` и `input`, необязательное `embedding_types`
(по умолчанию `["dense"]`). Сообщение может содержать несколько текстов.
В текущей конфигурации один воркер выполняет задачи последовательно:
увеличение окна нагрузки увеличивает число ожидающих задач, а не GPU-процессов.

## Что проверяется

- Окна из **1, 8, 32, 128** незавершённых задач с постоянным пополнением.
  Каждый этап отправляет не больше 256 задач и прекращает добавление через 60 секунд;
  затем отдельно ждёт завершения до 600 секунд. Лимиты меняются аргументами.
- Короткие, средние и предельные тексты: бюджеты **32, 512, 8192 токена**
  при стандартных настройках. Длина измеряется настоящим токенизатором модели,
  вместе со специальными токенами; фактическое число записывается в отчёт.
- Батчи из **1, 8, 1024 текстов** при стандартных настройках.
  `MAX_TEXTS` и `MAX_INPUT_TOKENS` берутся из окружения контейнера.
- Все семь непустых комбинаций `dense`, `sparse`, `colbert`;
  русский, английский, китайский, арабский и emoji.
- Пустой батч, пустая строка, точный лимит токенов и текстов, превышения лимитов,
  отсутствие `input`, неверный тип текста, неизвестные/повторные/пустые типы
  эмбеддингов, лишнее поле.
- Ожидаемые ошибки должны завершиться `failed` с `inference_failed`.
  После них отправляется корректное сообщение для проверки работоспособности.
- Наличие результата у каждой успешной задачи; для первого доступного результата
  каждого этапа — схема, ID, порядок, выбранные типы, размеры векторов,
  конечность чисел и нормализация dense. По умолчанию полное чтение ограничено
  32 MiB: большие результаты явно помечаются как `skipped_size_limit`.

Обычная серия варьирует длину и батч для dense, а комбинации типов — на коротком
тексте. **`--matrix` проверяет полное произведение длин × батчей × типов × окон**,
включая длинный ColBERT и максимальные батчи. Это существенно более тяжёлая серия.
Тексты повторяемые и синтетические: результат относится именно к этим данным.

Некорректные запросы здесь намеренно доходят до воркера в корректной JSON-оболочке
Celery. HTTP API такие запросы обычно отсекает раньше. Тест не измеряет HTTP,
повреждённые протокольные пакеты или другие сериализаторы.

## Как запустить позднее

Запускать на отдельном стенде с уже работающим `celery-amd`, загруженной моделью,
доступной GPU и без сторонних клиентов. Должен работать ровно один AMD-воркер;
`celery-cpu` должен быть остановлен. Общая очередь не позволяет определить,
какой из двух одновременно работающих воркеров обработал сообщение.
Окружение генератора и запущенного воркера должно совпадать: после изменения
`.env` сначала пересоздайте стенд. Генератор проверяет `INFERENCE_DEVICE=amd`,
доступность Redis, пустую очередь и отсутствие `unacked` перед отправкой.
Успешная разминка проверяет, что задачи действительно выполняются.

Из корня проекта, PowerShell или bash, после подготовки AMD-стенда:

```powershell
docker compose run --rm --no-deps -v "${PWD}/super_test:/app/super_test" --entrypoint /app/.venv/bin/python celery-amd /app/super_test/celery_amd_capacity.py
```

Это отдельный процесс генератора в контейнере с зависимостями проекта.
Он не запускает второй воркер и не загружает вторую модель. `--no-deps`
означает, что Redis и основной AMD-воркер уже должны работать.
Монтирование нужно, потому что `super_test` не входит в существующий Docker-образ;
пересобирать образ ради добавленного теста не требуется.

Короткая первая серия только для короткого dense, без граничных сообщений:

```powershell
docker compose run --rm --no-deps -v "${PWD}/super_test:/app/super_test" --entrypoint /app/.venv/bin/python celery-amd /app/super_test/celery_amd_capacity.py --case tokens-32_batch-1_dense --windows 1,8,32 --messages 64 --stage-seconds 15 --skip-boundaries
```

Расширенная серия с большим окном и полным перебором:

```powershell
docker compose run --rm --no-deps -v "${PWD}/super_test:/app/super_test" --entrypoint /app/.venv/bin/python celery-amd /app/super_test/celery_amd_capacity.py --matrix --tokens 32,512,8192 --batches 1,8,32,1024 --windows 1,8,32,128,512 --messages 1024 --publishers 8 --stage-seconds 120 --drain-timeout 3600
```

Аргументы `--tokens` и `--batches` не должны превышать настройки воркера;
`--messages` должен быть не меньше самого большого окна.
`--case` можно повторять, названия имеют вид `tokens-512_batch-8_dense+sparse`;
для таких комбинаций включите `--matrix`. Есть отдельный сценарий `multilingual`.
Граничные сообщения выполняются после серии независимо от `--case`, если
не передан `--skip-boundaries`.

## Что будет в отчёте

Файл `super_test/results/celery-amd-<UTC-время>-<id>.json` и строка JSON на каждый
завершённый этап в stdout. Отчёт сохраняется после каждого этапа и при обработанной
ошибке или Ctrl+C; содержит ID всех запланированных задач для последующего разбора.
Принудительное убийство процесса не гарантирует сохранение текущего этапа.

| Поле | Значение |
| --- | --- |
| `initial_burst` | Сколько первых сообщений опубликовано, время и сообщений/с до подтверждения всех публикаций первого окна |
| `successful_tasks_per_second` | Успешные задачи/с за полный этап, включая заполнение окна и ожидание хвоста |
| `completion_interval_tasks_per_second` | Задачи/с между первой и последней успешной отметкой завершения воркера |
| `successful_texts_per_second` | Успешно обработанные тексты/с |
| `successful_input_tokens_per_second` | Входные токены успешных задач/с, включая спецтокены |
| `latency_seconds` | p50/p95/p99/max публикации, ожидания очереди, работы воркера, общего наблюдаемого времени |
| `published`, `succeeded`, `failed`, `unresolved` | Подтверждённые публикации и состояния задач |
| `payload_json_bytes` | Размер исходного JSON в UTF-8; без протокольной оболочки и кодирования Celery |
| `total_result_bytes` | Суммарный размер сохранённых результатов этапа |
| `peak_sampled_queue_depth` | Максимальная замеченная длина Redis-очереди |
| `peak_sampled_redis_used_memory_bytes` | Максимальная замеченная память всего Redis, включая брокер и результаты |
| `summary_by_case` | Наибольшее пройденное окно, первое окно с ошибкой, лучшая скорость для каждого сценария |

`initial_burst` измеряет публикацию вместе с созданием статуса и расходами
генератора; это не чистый Redis benchmark. Маленькое первое окно не даёт
надёжной оценки максимума брокера. Для этого увеличивайте окна и `--publishers`.
Опрос и выборочная проверка результата тоже создают нагрузку; интервал опроса
по умолчанию 0.05 секунды, на очень быстрых задачах генератор может ограничивать
скорость. Серверные времена требуют синхронизированных часов контейнеров.
`worker_seconds` считается по JobStore и не включает всю последующую запись
результата в Redis. Пиковые показатели снимаются периодически и могут пропустить
короткий всплеск. VRAM и загрузка GPU этим скриптом не измеряются.

## Ошибки и интерпретация предела

При неожиданной ошибке, недостающем результате или истечении ожидания тест
останавливает серию. Уже запланированные публикации и доставленные задачи могут
продолжиться; их ID остаются в отчёте. Ошибка публикации отмечается как
`publish_error_delivery_uncertain`: подтверждение могло потеряться после доставки,
поэтому сообщение не отправляется повторно и его статус продолжает отслеживаться.
Код завершения `1` означает ошибку/прерывание, `0` — пройденную заданную серию.

Успех всей серии записывается как
`configured_range_passed_maximum_not_proven`: это **нижняя граница проверенной
ёмкости**, а не доказанный абсолютный максимум. Расширяйте диапазон окон, батчей
и длительности до насыщения скорости либо ошибки. Сам по себе большой принятый
бурст не означает, что воркер может постоянно обрабатывать такой поток.
Ошибка на следующем окне также требует разбора причины: таймаут, OOM,
недоступность Redis и предел генератора имеют разный смысл.

Результаты и статусы не удаляются: применяется штатный TTL проекта (обычно сутки).
Поэтому рост памяти включает накопленные результаты предыдущих этапов, а не
только текущее окно. Следите за местом под Redis AOF и результатами: максимальные
батчи и ColBERT могут расходовать много RAM/VRAM и диска. Скрипт не очищает очередь,
не перезапускает контейнеры и не отменяет оставшиеся задачи.
