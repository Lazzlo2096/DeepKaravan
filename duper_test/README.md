# Скорость эмбеддингов через REST API

`batch_embeddings.py` вызывает **работающий REST API** для запросов с
**1, 128, 512, 1024, 2048 текстами**. Везде используется одна и та же строка
из `text.txt`. По умолчанию на каждый размер — 2 прогрева и 5 измерений.
Прогревы тоже вызывают API, но не входят в статистику скорости.

Клиент использует только стандартную библиотеку Python. Он не загружает модель,
не импортирует PyTorch, не подключается к Redis напрямую и не запускает воркер.
Обработка проходит штатным путём: REST API → очередь Celery/Redis → воркер →
сохранение результата → REST-ответ.

## Запуск

API, Redis и нужный воркер должны **работать**. Для текущего Windows AMD стенда
запустите сервис обычной командой `just up` из корня проекта, дождитесь готовности
модели, затем из `duper_test`:

```powershell
just                         # список команд без запросов к API
just run --repeats 10 --warmups 3 # все размеры, 10 измерений, 3 прогрева
just run --repeats 10 --warmups 3 --batch-sizes "1 128 512 1024"
just run --repeats 10 --warmups 0 --batch-sizes "1 128" # без прогревов
just quick                   # 1 и 128 текстов, 3 измерения, 1 прогрев
just options                 # справка без запросов к API
```

Адрес по умолчанию — `http://localhost:8000`. Другой адрес задаётся флагом:

```powershell
just run --repeats 5 --warmups 2 --batch-sizes "1 2" --base_url http://localhost:18091
```

Его также можно задать через `DUPER_TEST_API_URL`.
Поддерживаются оба написания: `--base-url` и `--base_url`.
Батчи можно перечислять как `--batch-sizes "1 2"` или `--batch-sizes 1 2`.
Из корня проекта: `just --justfile duper_test/justfile run --repeats 10 --warmups 3`.
Прежняя позиционная запись `just run 10 3` заменена именованными параметрами.
Just использует Python из `.venv`; путь можно переопределить через
`DUPER_TEST_PYTHON`. Сам тест работает и под другим Python без установки пакетов:

```powershell
python duper_test/batch_embeddings.py --base-url http://localhost:8000 --repeats 10 --warmups 3
```

Все параметры скрипта доступны через `just run`: `--timeout 600` задаёт бюджет
ожидания одной попытки, `--request-timeout 90` — сетевой таймаут HTTP-вызова.
Есть `--batch-sizes`, `--text-file`, `--output-dir`.
Файл текста читается один раз как UTF-8, завершающие переводы строк убираются.
В отчёте сохраняются строка и её SHA-256.

## Как выполняется замер

Каждая попытка отправляет **один** `POST /v1/embeddings`:

```json
{"input": ["одинаковый текст", "одинаковый текст"], "embedding_types": ["dense"]}
```

Успех — только `200` с готовыми эмбеддингами в ответе на POST.
Опроса результата через GET нет. При `202` бенчмарк записывает ошибку и известный
`task_id`, затем останавливает серию: задача ещё может выполняться на сервере.
Повторных POST для той же попытки нет.

Время считается от начала подготовки POST до получения и разбора готового
JSON-ответа. Оно включает передачу запроса, валидацию на API, очередь, инференс,
сохранение, сериализацию и скачивание результата в том же POST-ответе.
Проверка числа векторов, индексов, формата task_id, размерности 1024, конечности чисел
и нормализации выполняется после остановки таймера.

Один текст даёт один dense-эмбеддинг, поэтому `эмбеддингов/с = текстов/с`.
Это скорость выполнения запросов через сервис, а не чистая скорость GPU.
Посторонние задачи в общей очереди влияют на результат.

## Батч 2048 и настройки сервиса

Размер батча здесь означает **число текстов в HTTP-запросе**. Скрипт отправляет
2048 одним запросом и никогда не разбивает его на несколько меньших.
Текущие `EmbeddingRequest.input` и `Settings.max_texts` ограничены 1024:
поэтому **2048 ожидаемо получит HTTP 422** и не получит значения скорости.
Тест не меняет лимиты приложения. Отказ записывается для каждой попытки,
включая измерения после прогревов; другие размеры продолжают проверяться.

`INFERENCE_BATCH_SIZE` на сервере определяет внутренний размер порции модели.
Например, запрос на 512 текстов может выполняться порциями по 8. Этот тест
не меняет настройки воркера и не утверждает, что все тексты вычислялись одним
GPU-вызовом. Доступную GPU и модель выбирает запущенный сервер.

## Отчёты и ошибки

Новые отчёты имеют имена `results/rest-batch-embeddings-<UTC-время>-<id>.json`
и `.csv`. В JSON есть `transport: REST`, адрес сервера, все прогревы и повторы,
HTTP-коды, ошибки, известные `task_id`, время POST и размер ответа.
CSV содержит сводку по каждому размеру. Отчёты сохраняются после каждой попытки
и при обработанном прерывании.

Колонка `batch time, s` в консоли и поле `batch_total_seconds` в JSON/CSV —
общее время измеряемой серии для одного размера батча, **без прогревов**.
Таймер запускается после прогревов, перед первым измеряемым повтором; включает
неудачные измеряемые попытки, проверку ответов и промежуточное сохранение отчётов.
При обработанной ошибке или Ctrl+C сохраняется время измеряемой серии до остановки.
Если остановка произошла на прогреве, время серии равно 0, `started_at` — null.
В JSON `started_at` отмечает начало измеряемой серии, `finished_at` — завершение.

Для успешных измерений считаются **среднее, медиана, минимум и максимум**
отдельно по времени и эмбеддингам/с. Среднее скорости — арифметическое среднее
`число текстов / секунды` по повторам. Дополнительно есть общая скорость:
`число успешных текстов / сумма времени успешных попыток`.
Прогревы и ошибки исключаются из статистики скорости. Ошибки учитываются явно;
если успехов нет, значения скорости пустые/null, а не нулевые.

В консоли для каждого размера выводится `POST responses/s` — число ответов
на POST в секунду, в порядке **среднее / медиана / минимум / максимум**.
Для каждого успешного повтора скорость считается как `1 / время POST`;
затем статистика считается по этим скоростям. Например, 2.323 секунды на запрос
соответствуют примерно 0.430 ответа/с. Запросы последовательные: это не замер
максимальной пропускной способности при конкурентных клиентах.

Сводка сохраняется в JSON как `responses_per_second`, а в CSV — как
`responses_per_second_mean/median/min/max`. Исходные времена также сохраняются
в полях `submit_seconds` и `seconds`. Учитываются только успешные измеряемые
повторы; прогревы исключены.

Сам API по-прежнему может вернуть 202 после `SYNC_TIMEOUT_SECONDS`.
Чтобы длинные запросы завершались ответом 200, увеличьте этот таймаут в настройках
сервера и примените настройки; сетевой таймаут клиента должен быть больше него.
Удаление опроса в бенчмарке не меняет поведение сервера.

Ответ 422 означает завершённый отказ валидации либо ошибку инференса; повторения
и следующие размеры продолжаются. При сетевой ошибке, таймауте или другом
неожиданном HTTP-ответе серия останавливается: задача может ещё выполняться,
и продолжение исказило бы следующие замеры. Задания не отменяются и не
отправляются повторно. При Ctrl+C также может остаться работа на сервере;
известный ID сохранится в JSON.

Код завершения 0 — все попытки успешны; 1 — ошибки или прерывание. Серия,
включающая отклонённый запрос на 2048, завершится с кодом 1 и сохранит отчёт.

Старые файлы `batch-embeddings-...` относятся к прежнему прямому тесту модели.
Они оставлены на месте и напрямую с новыми REST-замерами не сравнимы.
После переделки нагрузочный тест не запускался.
